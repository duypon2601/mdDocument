Kiến trúc & Vận hành

Temporal hoạt động thế nào?

Một góc nhìn trực quan, súc tích về cách Temporal giữ cho các luồng xử lý dữ liệu nhiều bước chạy trơn tru, không lo mất mát khi máy chủ gặp sự cố.

💡 Hình dung Temporal như một văn phòng quản lý dự án
🧑‍💼 Khách hàng (Client) Gửi phiếu yêu cầu một công việc (ví dụ: bóc tách file PDF, tạo đơn hàng).
📖 Thư ký & Sổ cái (Temporal Server) Đánh số ID, ghi từng bước vào cuốn sổ nhật ký không thể xoá, rồi thả phiếu vào hộp thư.
📬 Hộp thư nhận việc (Task Queue) Nơi chứa việc chờ xử lý. Nhân viên rảnh sẽ tự tới rút việc về làm.
📋 Quản đốc điều phối (Workflow) Cầm bản quy trình chỉ đạo: "Làm bước 1 trước, nếu xong thì làm bước 2". Không trực tiếp bốc vác hay gọi điện thoại.
🔨 Nhân viên thực thi (Activity) Tự tay làm việc cụ thể: bóc tách văn bản, gọi AI, ghi dữ liệu vào database.
🛡️ Cúp điện giữa chừng? Nhân viên mới mở sổ nhật ký ra xem. Bước nào xong rồi thì không làm lại, làm tiếp ngay bước đang dở.

Mô hình kiến trúc tổng thể

Sự tách biệt rõ ràng giữa Client, Server trung tâm và các Worker.

5 Thành phần tạo nên hệ thống

Nắm vững 5 khái niệm này là đủ hiểu cách vận hành của mọi hệ thống dùng Temporal.

Client

Client

Phần mềm của bạn (ví dụ FastAPI hoặc CLI). Client kết nối với Temporal Server để khởi động job mới, tra cứu tiến độ hoặc yêu cầu huỷ.

Temporal Server

Temporal Server

Hệ thống máy chủ lưu trữ toàn bộ lịch sử (Event History), duy trì hàng đợi (Task Queue), quản lý Timer chờ đợi và tự động kích hoạt retry.

Task Queue

Task Queue

Hàng đợi định danh (ví dụ convert-tq). Server đẩy việc vào đây, Worker định kỳ thăm dò (long-polling) để kéo việc về làm.

Workflow

Workflow (Điều phối)

Đoạn code định nghĩa quy trình: bước nào trước, bước nào sau, timeout bao lâu. Tuyệt đối không làm I/O hay gọi mạng trong này.

Activity

Activity (Thực thi)

Nơi làm công việc thực tế: gọi API bên ngoài, bóc tách tài liệu Docling/OCR, ghi dữ liệu vào cơ sở dữ liệu hoặc kho lưu trữ S3/MinIO.

Xem luồng hoạt động từng bước

Bấm vào từng bước hoặc dùng nút chạy tự động để quan sát các thành phần tương tác.

Đang tác động: Client Temporal Server Task Queue Workflow Activity
1
Client gửi yêu cầu bắt đầu Workflow
Client Server

Khách hàng hoặc API gọi client.start_workflow() với tên Workflow, dữ liệu đầu vào (Input Payload) và ID duy nhất (ví dụ ingest-doc-123).

Sự kiện ghi vào lịch sử: WorkflowExecutionStarted
2
Server xếp việc vào Task Queue
Server Task Queue

Temporal Server ghi nhận job vào Event History và đẩy một Workflow Task vào Task Queue định sẵn (ví dụ: ingest-tq) để chờ Worker nhận.

Hàng đợi này tách biệt hoàn toàn giữa người giao việc và người làm việc, giúp hệ thống không bị nghẽn tải.
3
Worker nhận Task và khởi chạy Workflow
Task Queue Workflow

Worker đang long-polling trên hàng đợi sẽ kéo Workflow Task về và chạy hàm run() của Workflow trong bộ nhớ.

Sự kiện ghi vào lịch sử: WorkflowTaskStarted
4
Workflow ra lệnh gọi Activity
Workflow Server Task Queue

Trong hàm run, code gặp lệnh workflow.execute_activity("convert_document", ...). Workflow không tự thực thi mà thông báo lại cho Server: "Hãy lên lịch chạy Activity này cho tôi".

Sự kiện ghi vào lịch sử: ActivityTaskScheduled
5
Worker thực hiện Activity (Làm việc thực tế)
Task Queue Activity

Một Worker lắng nghe queue đó (có thể là máy chủ khác có GPU/CPU chuyên dụng) nhận task về và bắt đầu thực hiện: đọc file PDF, chạy OCR, gọi LLM, tính toán nặng.

Sự kiện ghi vào lịch sử: ActivityTaskStarted
6
Activity hoàn thành và trả kết quả về Server
Activity Server

Hàm Activity kết thúc thành công và gửi kết quả về Server. Server lưu ngay kết quả này vào sổ cái Event History.

Sự kiện ghi vào lịch sử: ActivityTaskCompleted (kèm output)
7
Workflow hoàn tất và Client nhận kết quả
Workflow Server Client

Server kích hoạt lại Workflow để đi tiếp các bước tiếp theo hoặc kết thúc nếu đã xong tất cả. Khi Workflow trả về giá trị cuối cùng, Client lấy được dữ liệu qua handle.result().

Sự kiện ghi vào lịch sử: WorkflowExecutionCompleted
⚡ Sức mạnh cốt lõi: Khả năng sống sót khi máy chủ gặp sự cố (Durable Execution)

Trong hệ thống thông thường, nếu máy chủ chết giữa chừng, toàn bộ bộ nhớ RAM biến mất, job bị huỷ hoặc phải chạy lại từ đầu. Với Temporal, nhật ký được lưu tại Server độc lập, cho phép worker mới tua lại lịch sử (Replay) và tiếp tục như chưa hề có sự cố.

1
Bước 1 (Parse PDF) đã xong, đang chạy Bước 2 (Gọi LLM)
Workflow Activity

Bước Parse tài liệu đã xong và kết quả đã nằm an toàn trong Event History trên Server. Worker đang tiến hành bước 2 thì máy chủ đột ngột sập nguồn hoặc hết RAM (OOM Killer).

2
Server phát hiện Worker đã ngừng hoạt động
Server

Do Worker không gửi tín hiệu Heartbeat hoặc quá thời gian start_to_close_timeout, Server nhận ra Worker cũ đã chết và đưa task trở lại Task Queue để tìm Worker khác.

Sự kiện: ActivityTaskTimedOut hoặc phân bổ lại task
3
Worker mới tiếp nhận và thực hiện "Replay"
Task Queue Workflow Server

Một Worker khác trong cụm kéo Workflow Task về và chạy lại mã từ đầu. Điều kỳ diệu nằm ở đây: khi đến dòng lệnh gọi bước 1, SDK thấy trong Event History đã có kết quả ActivityTaskCompleted, nên lập tức trả về kết quả cũ mà không chạy lại bước 1 thật!

Không tốn tiền gọi lại API đắt đỏ, không mất thời gian xử lý lại dữ liệu cũ, không tạo ra side effect lặp.
4
Chạy tiếp bước 2 còn dở dang
Workflow Activity Server

Sau khi tua qua bước 1 trong tích tắc, Workflow chạm tới bước 2 và kích hoạt Activity thực hiện lại. Quy trình tiếp tục trôi chảy cho tới khi hoàn tất.

1
Activity gặp lỗi mạng tạm thời (429 Rate Limit / 503)
Activity Server

Khi gọi API bên ngoài bị nghẽn mạng, Activity raise Exception bình thường. Server bắt được lỗi và tự động áp dụng RetryPolicy (thử lại sau 2s, 4s, 8s...). Trong thời gian chờ này, Worker được giải phóng làm việc khác.

2
Client tra cứu trạng thái tức thì (Query)
Client Workflow

Bất cứ lúc nào trong khi job đang chạy, người dùng hoặc Web frontend có thể gọi handle.query("get_progress") để lấy % tiến độ hoặc trạng thái nội bộ mà không làm gián đoạn workflow.

Query là thao tác chỉ đọc (Read-only), không được phép thay đổi trạng thái của Workflow.
3
Workflow tạm dừng chờ người duyệt (Durable Wait)
Workflow Server

Quy trình yêu cầu có người duyệt trước khi nạp dữ liệu. Workflow gọi lệnh chờ: await workflow.wait_condition(...). Trạng thái được đông kết, tài nguyên RAM CPU được giải phóng hoàn toàn. Việc chờ đợi có thể kéo dài vài giờ, vài ngày hoặc vài tháng.

4
Quản trị viên bấm Duyệt -> Gửi Signal đánh thức
Client Server Workflow

Người duyệt bấm Approve trên web dashboard. Client gọi handle.signal("review_decision", approved=True). Server nhận tín hiệu, ghi sự kiện WorkflowExecutionSignaled và lập tức đánh thức Workflow tiếp tục chạy.

3 Nguyên tắc vàng khi viết code

Để tận dụng trọn vẹn khả năng phục hồi của Temporal mà không bao giờ gặp lỗi ngớ ngẩn.

1

Workflow phải Deterministic

Khi replay, code workflow sẽ chạy lại từ dòng 1 và phải tạo ra đúng chuỗi lệnh như lần chạy trước. Nếu kết quả rẽ nhánh khác đi, hệ thống sẽ báo lỗi Non-Determinism.

❌ Không gọi datetime.now(), random(), uuid4()
❌ Không gọi API, không đọc ghi file trên đĩa trong Workflow
✅ Dùng workflow.now(), workflow.uuid4()
✅ Toàn bộ I/O chuyển hết vào Activity
2

Activity phải Idempotent

Activity có thể bị chạy lại nhiều lần do mạng chập chờn hoặc retry. Chạy lại cùng một tham số đầu vào phải luôn cho ra cùng kết quả và không gây tác dụng phụ lặp.

❌ Không sinh tên file bằng timestamp ngẫu nhiên khi ghi đĩa
❌ Không thực hiện trừ tiền mà thiếu khoá chống trùng (idempotency key)
✅ Tên file và ID tài nguyên sinh trực tiếp từ mã đơn hàng / input
✅ Ghi dữ liệu theo cơ chế Upsert hoặc "ghi nếu chưa có"
3

Payload nhỏ và tự chứa

Mọi tham số đầu vào và đầu ra đều truyền qua Temporal Server và được lưu vĩnh viễn vào Event History. Cần giữ payload gọn nhẹ để hệ thống luôn nhanh.

❌ Không trả về nội dung file raw cả chục MB trong kết quả
❌ Không truyền đường dẫn file local (/tmp/...) giữa các bước vì mỗi bước có thể chạy ở máy khác nhau
✅ Lưu file lớn vào MinIO/S3, chỉ truyền mã file_id

Code thực tế trông như thế nào?

Mẫu code Python chuẩn với SDK temporalio theo đúng nguyên tắc trên.

Python SDK 
# workflow.py - Chỉ điều phối, không làm I/O
from datetime import timedelta
from temporalio import workflow
from temporalio.common import RetryPolicy

@workflow.defn(name="IngestDocumentWorkflow")
class IngestDocumentWorkflow:
    def __init__(self):
        self._progress = "Khởi tạo"

    @workflow.query(name="get_progress")
    def get_progress(self) -> str:
        return self._progress

    @workflow.run
    async def run(self, doc_id: str) -> dict:
        self._progress = "Đang bóc tách văn bản"
        # 1. Gọi Activity chuyển đổi PDF sang Markdown
        doc_data = await workflow.execute_activity(
            "convert_document",
            doc_id,
            start_to_close_timeout=timedelta(minutes=5),
            retry_policy=RetryPolicy(maximum_attempts=3),
        )

        self._progress = "Đang tạo vector embedding"
        # 2. Gọi Activity chunking & embedding
        result = await workflow.execute_activity(
            "index_chunks",
            doc_data,
            start_to_close_timeout=timedelta(minutes=2),
        )

        self._progress = "Hoàn tất"
        return {"status": "SUCCESS", "chunks_indexed": result["count"]}
# activity.py - Nơi làm việc nặng và thao tác I/O
from temporalio import activity
from temporalio.exceptions import ApplicationError

@activity.defn(name="convert_document")
async def convert_document(doc_id: str) -> dict:
    # Đọc file từ MinIO / S3 bằng doc_id (Idempotent)
    raw_path = await download_from_storage(doc_id)
    if not raw_path:
        # File không tồn tại thì không retry vô ích
        raise ApplicationError("Không tìm thấy file", non_retryable=True)
    
    # Gửi heartbeat nếu tiến trình xử lý kéo dài nhiều trang
    activity.heartbeat("Đang chạy OCR trang 1...")
    markdown_content = await run_docling_ocr(raw_path)

    return {"doc_id": doc_id, "text_length": len(markdown_content)}
# client.py - Giao diện khởi động và kiểm tra
from temporalio.client import Client

async def main():
    client = await Client.connect("localhost:7233")

    # Khởi động Workflow với ID duy nhất
    handle = await client.start_workflow(
        "IngestDocumentWorkflow",
        "doc-contract-2026.pdf",
        id="ingest-doc-contract-2026",
        task_queue="ingest-tq",
    )

    # Truy vấn tiến độ bất kỳ lúc nào
    progress = await handle.query("get_progress")
    print(f"Tiến độ hiện tại: {progress}")

    # Chờ kết quả cuối cùng
    res = await handle.result()
    print(f"Kết quả: {res}")

Tại sao không dùng giải pháp thông thường?

Bảng đối chiếu cụ thể giữa Temporal và các mô hình xử lý nền quen thuộc.

Tiêu chí Cron Job / Script thường Celery / RabbitMQ Temporal
Khi máy chủ cúp điện / chết RAM Mất sạch dữ liệu trong RAM. Chạy lại từ đầu. Task bị đẩy lại queue nhưng phải tự xử lý việc bước nào đã làm dở. Tự phục hồi: Tua lại lịch sử, chỉ chạy tiếp đúng bước đang dở.
Theo dõi tiến trình nhiều bước Tự viết bảng DB, tự cập nhật từng cờ trạng thái bằng tay. Phải tự nối dây (chaining/canvas), khó debug khi lỗi ở giữa. Tự nhiên: Viết code tuần tự await a(); await b(); như hàm thường.
Chờ duyệt (Human-in-the-loop) Rất khó hoặc phải viết webhook phức tạp. Khó giữ trạng thái chờ dài hạn (hàng ngày, hàng tuần). Đơn giản: Chờ bằng Signal, ngủ hàng tháng không tốn CPU.
Quan sát & Debug Đọc file log khổng lồ để tìm dòng lỗi. Xem trạng thái task trên Flower hoặc Celery UI. Web UI đầy đủ: Xem rõ từng input, output, lỗi stack trace của từng bước.

Câu hỏi thường gặp

Temporal Server có chạy code của tôi không?

Không. Temporal Server không bao giờ chạy code Python/Go của bạn. Server chỉ đóng vai trò bộ não điều phối: ghi nhận sự kiện vào database, quản lý Task Queue, tính giờ timer và gửi task cho Worker. Code của bạn hoàn toàn chạy trên máy chủ Worker.

Tại sao trong Workflow không được dùng time.sleep() hay datetime.now()?

Vì cơ chế phục hồi dựa trên Replay (tua lại lịch sử). Khi replay, hàm Workflow chạy lại từ đầu. Nếu bạn dùng datetime.now(), mỗi lần chạy lại sẽ ra một mốc thời gian khác nhau, phá vỡ tính nhất quán (Non-determinism). Khi cần lấy giờ, Temporal cung cấp hàm workflow.now() luôn trả về đúng mốc thời gian lúc sự kiện đó thực sự diễn ra trong lịch sử.

Tôi có thể huỷ (Cancel) một job đang chạy không?

Có. Bạn có thể gọi handle.cancel() từ Client hoặc bấm Cancel trên giao diện Temporal Web. Workflow sẽ nhận được thông báo huỷ và có thể thực hiện dọn dẹp tài nguyên (rollback/cleanup) nếu cần.

Task Queue khác gì so với Message Queue thông thường như Kafka hay RabbitMQ?

Trong Kafka hay RabbitMQ, bạn là người chịu trách nhiệm giữ trạng thái của toàn bộ tiến trình phân tán. Với Temporal, Task Queue chỉ là một ống dẫn việc nội bộ. Temporal Server quản lý trạng thái, retry, timeout và logic điều phối tổng thể, bạn không phải đau đầu thiết kế hàng đợi trung gian.
