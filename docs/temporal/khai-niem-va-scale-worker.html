🧩 1. Mổ xẻ 4 Khái Niệm Trụ Cột (The 4 Pillars)
Deep Dive
📋 Workflow
Điều phối / Orchestrator
Ẩn dụ đời thường: "Tổng chỉ huy công trình" hoặc "Bản vẽ thi công". Chỉ huy không tự tay vác xi măng, mà vạch ra trình tự: Bước 1 đào móng, Bước 2 đổ cột, Bước 3 lợp mái.

Là đoạn code Python đóng vai trò nhạc trưởng định nghĩa quy trình kinh doanh. Workflow quyết định thứ tự thực thi, điều kiện rẽ nhánh, timeout, và chính sách retry.

  • ✔ Deterministic (Đơn định tuyệt đối): Chạy lại 1000 lần với cùng input phải cho ra cùng các lệnh gọi.
  • ✔ Replay State: Khi Worker bị sập, một Worker khác nạp lịch sử (History) từ Temporal Server và chạy lại từ đầu để dựng lại đúng trạng thái đang dở.
  • ✖ CẤM TUYỆT ĐỐI: Không được gọi REST API, không query DB, không datetime.now(), không random() trực tiếp trong Workflow!
@workflow.defn class DocumentPipelineWorkflow: @workflow.run async def run(self, doc_id: str): # Chỉ điều phối gọi Activity, KHÔNG tự làm I/O text = await workflow.execute_activity( ocr_file_activity, doc_id, start_to_close_timeout=timedelta(minutes=5) ) return await workflow.execute_activity(extract_info_activity, text)
🔨 Activity
Thực thi / Worker Task
Ẩn dụ đời thường: "Người thợ chuyên môn" (thợ hàn, thợ mộc). Nhận bản vẽ từ chỉ huy để làm một việc cụ thể: đục tường, sơn nhà. Làm xong thì bàn giao thành phẩm hoặc báo hỏng để thử lại.

Là nơi chứa toàn bộ công việc thực tế (side-effects & heavy lifting): gọi model LLM, bóc tách OCR, đọc ghi database Postgres, gọi REST API ngoài, xử lý ảnh.

  • ✔ Non-deterministic thoải mái: Được phép gọi mạng chập chờn, query database, tính toán ngẫu nhiên, ghi file vào ổ cứng.
  • ✔ Tự động Retry siêu mạnh: Cấu hình Exponential Backoff. Nếu API của OpenAI bị 429 hay mạng đứt, Temporal tự retry mà không làm hỏng Workflow.
  • ✔ Heartbeat: Với tác vụ lâu (như render video 30 phút), Activity gửi nhịp tim định kỳ về Server để chứng minh nó chưa bị treo máy.
@activity.defn async def ocr_file_activity(doc_id: str) -> str: # Nơi làm việc nặng thực sự (Tốn CPU/RAM/IO) file_bytes = await download_from_s3(doc_id) text = run_heavy_ocr(file_bytes) return text
📬 Task Queue
Hàng đợi định tuyến
Ẩn dụ đời thường: "Hộp thư / Khay để phiếu việc". Chỉ huy thả phiếu giao việc vào khay có dán nhãn: "Hộp việc OCR", "Hộp việc AI". Thợ nào rảnh thì tự thò tay vào lấy một phiếu đi làm.

Là hàng đợi trung gian (Queue) nằm trên Temporal Server, được định danh đơn giản bằng một chuỗi chuỗi ký tự (ví dụ: "doc-processing-queue").

  • ✔ Cơ chế PULL (Long-Polling): Server KHÔNG bắn task vào IP Worker. Worker chủ động mở kết nối gRPC hỏi: "Có việc không?". Rảnh thì nhận, bận thì thôi.
  • ✔ Decoupling (Phân tách hoàn toàn): Client & Server không cần biết Worker đang chạy ở đâu, bao nhiêu máy, sau NAT hay Firewall đều chạy ngon lành.
  • ✔ Tự động cân bằng tải (Load Balancing): Không cần Nginx / Load Balancer đứng trước Worker. Worker nào rảnh tay thì nhặt việc trước.
# Không cần cấu hình trước trên Server, tự tạo theo tên khi có Worker lắng nghe TASK_QUEUE_NAME = "pdf-extraction-queue" # Client bắn việc vào Queue: await client.start_workflow(DocWorkflow.run, id="job-1", task_queue=TASK_QUEUE_NAME)
⚙️ Worker
Tiến trình máy chủ thực
Ẩn dụ đời thường: "Đội ngũ nhân công đang ngồi ở công xưởng". Là những người có cơ bắp, tốn cơm ăn nước uống (tốn CPU/RAM của máy thật) để cày cuốc công việc.

Là tiến trình Python (Service / Docker Container / K8s Pod) do bạn viết và vận hành. Đây là nơi duy nhất lưu trữ code Workflow & Activity trong RAM.

  • ✔ Temporal Server KHÔNG LƯU CODE: Server chỉ lưu lịch sử dạng JSON. Worker mới là nơi nạp code Python vào bộ nhớ để chạy.
  • ✔ Vòng lặp bất tận (Long Poll Loop): Worker cắm kết nối gRPC liên tục vào Task Queue để rình việc, giải mã task, thực thi hàm và gửi lại kết quả.
  • ✔ Chết không mất việc: Nếu Worker đang chạy mà bị OOM hay đứt điện, Server phát hiện qua timeout và nhả task lại vào Task Queue cho Worker khác làm tiếp!
# File worker.py chạy trong Docker/Pod: worker = Worker( client, task_queue="pdf-extraction-queue", workflows=[DocumentPipelineWorkflow], # Nạp code vào RAM activities=[ocr_file_activity, extract_info_activity] ) await worker.run() # Bắt đầu poll việc

⚡ 3. Bản Chất Cốt Lõi: Tại Sao Nói "Scale Là Scale Worker"?
Bản Chất Hệ Thống
💡
"Trong Temporal: Tải nặng nề nhất nằm ở việc thực thi mã nguồn. Temporal Server chỉ giữ hàng đợi và sự kiện. Do đó, muốn mở rộng năng lực xử lý (Throughput), bạn chỉ cần cắm thêm Worker!"

Khi xây dựng hệ thống xử lý dữ liệu và trích xuất thông tin tài liệu, các tác vụ như nhận dạng OCR, chia nhỏ file PDF, bóc tách bảng biểu, gọi mô hình AI Gemini/OpenAI, embedding vector ngốn 99% CPU, GPU, RAM và thời gian chờ mạng. Temporal được thiết kế theo tư duy phân tách triệt để:

1
Server Không Chạy Code Của Bạn
Temporal Server viết bằng Go/Java, nó chỉ làm việc nhẹ: ghi event log vào Postgres/Cassandra và giữ Task Queue. Nó không tốn 1MB RAM nào để load mô hình OCR hay parse PDF. Do đó, 1 Server cụm nhỏ có thể điều phối hàng triệu task mà không hề đuối sức.
2
Cơ Chế Pull (Không Bị Sập Kéo Theo)
Trong kiến trúc REST cổ điển, nếu user gửi 10.000 file một lúc thì web server sẽ sập vì quá tải connection (OOM/504). Trong Temporal, 10.000 file chỉ biến thành 10.000 task nằm yên trong Task Queue. Worker cứ bình tĩnh lấy từng cái làm, không bao giờ bị sập theo hình thức cascading failure.
3
Bật Thêm Worker Là Tăng Tốc Tức Thì
Không cần restart Temporal Server, không cần sửa config router hay Nginx. Muốn giải quyết hàng đợi nhanh hơn? Bạn chỉ cần tăng số lượng Docker Container / K8s Pod chạy python worker.py từ 2 Pod lên 20 Pod. Chúng sẽ tự động chia nhau kéo task trong Task Queue về làm song song!

🚀 Thực tế triển khai: Tự động co giãn (Horizontal Pod Autoscaler / KEDA)

Trong môi trường production, DevOps chỉ cần cấu hình metric temporal_task_queue_backlog (số lượng task đang chờ trong Task Queue):
• Khi hàng đợi có > 500 tasks ➔ K8s tự động bật thêm Worker Pods (Scale Out).
• Khi hàng đợi cạn (rảnh việc) ➔ K8s tự thu hồi Worker Pods về mức tối thiểu để tiết kiệm tiền cloud (Scale In).

Matrix Phân Biệt
Tiêu chí Workflow (Nhạc trưởng) Activity (Thợ thi công)
Bản chất Mô tả thứ tự logic kinh doanh, luồng đi của dữ liệu. Thực thi một bước công việc độc lập, nặng nhọc.
Tính đơn định (Determinism) Bắt buộc 100%. Chạy lại với cùng input phải ra chuỗi event y hệt (để Replay). Tùy ý (Non-deterministic). Được phép gọi mạng, query DB, phụ thuộc thời gian thực.
Nơi thực thi I/O & Gọi Model AI ❌ Tuyệt đối cấm thực hiện I/O trực tiếp. ✔ Chuyên trách gọi REST API, LLM, OCR, ghi Postgres, đọc file S3.
Cơ chế tự hồi phục khi lỗi Khi Worker sập, Server bảo Worker khác nạp lại History để Replay khôi phục biến trong RAM. Tự động thử lại (Retry Policy) với Backoff. Nếu hỏng vĩnh viễn mới ném Exception về Workflow.
Scale khi tải tăng Workflow Task rất nhẹ, thường chỉ tiêu tốn vài mili-giây CPU để quyết định bước tiếp theo. Điểm nghẽn tài nguyên chính (ngốn 95% CPU/GPU). Cần scale nhiều Activity Worker.

🎯 6. Trắc Nghiệm Tình Huống: Kiểm Tra Độ Hiểu Sâu
Tự Đánh Giá
Câu 1: Bạn muốn gọi API của OpenAI để tóm tắt văn bản. Bạn phải viết hàm gọi này ở đâu?
Chính xác! Lời gọi API mạng ra ngoài là tác vụ có side-effects và non-deterministic, bắt buộc phải viết trong Activity. Nếu viết trực tiếp trong Workflow, cơ chế Replay của Temporal sẽ bị phá vỡ!
Câu 2: Khi lượng tài liệu upload đột ngột tăng gấp 50 lần vào giờ cao điểm, bạn cần làm gì để hệ thống không bị nghẽn?
Chính xác! Bản chất "Scale là scale worker": Toàn bộ task dồn vào Task Queue được giữ an toàn trên Server. Tăng số lượng Worker sẽ giúp tăng năng lực gắp task và xử lý đồng thời. Worker kết nối ra ngoài bằng Long-poll nên không cần mở port hay load balancer.
Câu 3: Temporal Server biết Workflow gồm những bước nào bằng cách nào nếu nó không hề lưu code Python của bạn?
Chính xác! Server không có code. Khi cần chạy, Server phát tín hiệu cho Worker. Worker lôi hàm trong RAM ra chạy. Khi gặp execute_activity, Worker gửi một Command về báo: "Tôi cần chạy activity này", lúc đó Server mới tạo Activity Task vào queue.
